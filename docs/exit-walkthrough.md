# 退驻责任串联：代表权更换、保留地址与旧件转寄未明

本文用一条贯穿业务线说明：企业搬离工位后，为什么不能只打一个“已退驻”标签，以及运营如何从**一个退驻申请**查到哪些责任已结束、哪些仍未结。所有编号为合成资料。

## 背景

合成创业企业甲（CO-1）原代表为 PER-A，入驻含两项服务：`office` 空间使用至 2026-11-30，`address` 地址托管至 2026-12-31。企业实际已搬离工位，但：

- 代表权正在由 PER-A 更换为 PER-B；
- 企业付费保留一段地址，前台仍可能收到挂号通知与包裹；
- 一件旧件 MAIL-1 已申请外部转寄，承运台受理情况尚未查明。

## 第一步：代表权更换，新接收授权必须重新核实

1. 运营登记 PER-B 的代表权（`POST /representations`，状态 `pending`），核实后生效（`POST /representations/:id/verify`）。
2. 系统自动把 PER-A 的旧代表权置为 `superseded`；同企业所有 `active` 的授权领取人置为 `reverify`。注意区分两件事：
   - **已经合法领取的事实保留**：已 `delivered` 的来件事件不回滚；
   - **尚未领取的件不能再凭旧授权领取**：授权须由运营重新核实（`POST /recipient-auths/:id/verify`）。
3. 一个自然人可代表多家企业（PER-A 仍可保留 CO-2 代表权），但企业授权与个人门禁是两套数据：门禁凭证锚定企业服务关系，不因为“同一个人”而通用。
4. 若新旧代表对某未领取件有争议，任一方可 `POST /disputes`：该件 `blocked=true`、交付暂停；空间、地址等普通办公服务**不**因此全部停用。争议只能由复核员（reviewer）独立结案，提出人不能自行解除。

## 第二步：退驻申请把结束动作拆成四个维度

企业 `POST /exits`，声明 `officeEnd=2026-11-30`、`addressEnd=2026-12-31`。运营在 `GET /exits/:id/overview` 看到的不是单一标签，而是六个责任面：

| 责任面 | 判定依据 | 本例初始状态 |
| --- | --- | --- |
| 空间使用 space | office 服务是否截止 | open，待勾选 |
| 人员进出 access | 是否还有 `issued/return_pending` 凭证 | open，KEY-1 未还 |
| 地址托管 address | address 服务是否仍覆盖当日 | active，保留至 12-31 |
| 未结来件 mail | 非 delivered/rejected/returned 的件与在途转寄 | open，MAIL-1 转寄未明 |
| 争议 disputes | 是否有 open 争议 | 视争议处理而定 |
| 押金 deposit | 是否还有自由余额或暂扣 | open，DEP-1 未结 |

逐项交接顺序与约束：

1. `checkpoints/space`：office 服务截止，企业转 `exiting`；address 不受影响。
2. 归还钥匙：`POST /credentials/KEY-1/return` 后凭证进入 `return_pending`，**同一钥匙立即不能再入场**（入场尝试留痕并 403）；`return-confirm` 后才能勾选 `checkpoints/access`。
3. `checkpoints/address`：地址截止到 12-31，因晚于空间结束日，自动生成一条付费保留记录（`retentions`）。
4. `checkpoints/mail`：存在未结来件或在途转寄时拒绝勾选。
5. `checkpoints/deposit` 与 `finalize`：全部检查点完成后才允许退驻结案。

## 第三步：保留地址期间与到期后的来件

- 保留期内（≤ 2026-12-31）：前台照常登记真实来件（件号、收件主体、到达时间、封装状态）。
  - 挂号通知（`requiresPrincipal`）只能由当前有效代表本人签收；时限临近又没有合格接收人时，`GET /mail/pending/deadlines` 明确列出待办，系统**不会**自动写成已送达。
  - 可拒收包裹允许登记即拒收；挂号通知不允许。
  - 扫描面单只存引用，不公开全文；前台视图收窄到交付所需字段。
- 地址到期后（> 2026-12-31）：新来件按企业约定处理，**不能因历史合同继续接收**：
  - 默认 `reject`：登记同时标记拒收；
  - 或 `verify`：进入 `verification_hold`，不进可领取库存，运营核实后再决定受理或拒收。

## 第四步：旧件转寄“受理未明”的处理

MAIL-1 在搬离前已 `POST /forwardings`：

1. 建立转寄后来件立即转 `forwarding`，与现场领取互斥——不能一边等转寄一边让人领走。
2. 若承运台网络中断或超时，转寄状态为 `unclear`：**受理未明不等于未受理**。系统保留原件责任，继续禁止现场领取，只允许 `POST /forwardings/:id/sync` 查单：
   - 查单找到流水（accepted/pending/confirmed）：受理成立，按承运状态推进；`confirmed` 后来件为 `forwarded`；
   - 查无流水且确认未受理：转寄 `carrier_rejected`，来件恢复 `pending`，可重新安排领取。
3. 撤销的边界：
   - 仅在**从未成功提交承运台**时，撤销才会把件恢复为可领取库存；
   - 已提交、受理未明或已实际转寄之后到达的撤销，一律登记为**拦截申请**（intercept），件不会恢复成可领取库存；拦截成功实物按“退回件”处理（`returned`），拦截失败则转寄继续。

## 第五步：押金结清不牵连无关余额，也不清空转寄责任

- 已确认费用逐项登记；争议暂扣必须关联争议 ID，且只冻结争议金额——不能为一个来件争议扣住全部无关余额。
- 退款金额先受自由余额约束（押金 − 费用 − 暂扣 − 已退），再受钥匙设备归还约束；超额退款与未归还凭证分别返回不同错误码。
- 即便押金已退，`GET /deposits/:companyId/summary` 仍单列 `openForwardingIds`：未完成的转寄责任不随退款清空。

## 运营视角的最终核对

打开 `GET /exits/:id/overview` 即可回答：

- 空间、人员进出是否已结束（凭证是否全部归还）；
- 地址托管是否仍在有效期、保留到哪一天；
- 哪些来件仍未结、哪些转寄在途或受理未明；
- 是否存在未结争议及其暂扣金额；
- 押金还有多少自由余额、多少暂扣、已退多少。

只有五个检查点全部完成，`POST /exits/:id/finalize` 才会把企业标记为 `exited`；在此之前，企业状态始终保留可追踪的中间责任，而不是一个无法解释的“已退驻”标签。
